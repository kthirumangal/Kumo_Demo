What this is

A relational foundation model, queried live

  • KumoRFM is pre-trained. There is no training run, no feature engineering, and no separate model per question.
  • You hand it linked tables and write a predictive query. It answers.
  • Churn, engagement, spend forecast and recommendations all come from one graph and one model — only the query changes.
  • Signal can come from other customers' behaviour, not just the rows belonging to the customer you are scoring.

Traditional ML vs this

  • Traditional: flatten tables into one wide row per entity, hand-build recency / frequency / ratio features, train a model per question.
  • KumoRFM: keep the tables and their foreign keys, let the model read the graph, add a new question by writing a new query.

Input

Three CSV files

  • data/customers.csv — 200 rows, one per customer
  • data/products.csv — 60 rows, the catalogue
  • data/transactions.csv — 7,120 rows, the events
  • Nothing is pre-aggregated. Raw transactional rows go in as-is; the model infers the graph from the keys.
  • CSV is only the transport — the SDK takes DataFrames, so the same code reads from Snowflake, Databricks, S3 or a database.

Scope

What is real, and what is not

  • The model is real. Every number in the prediction panel is returned by KumoRFM over the network.
  • The queries are real. The PQL shown on screen is exactly what is sent.
  • Anchor time is real — a genuine model parameter, not a UI effect.
  • The data is synthetic and seeded. Customers, products, districts and managers are invented.
  • District risk profiles were generated to make the rollup interesting.
  • The graphs depict the model's input, not its internal attention.
  • No confidence intervals. Company totals sum point estimates.

Setup · connecting to KumoRFM

Endpoint + key, from the environment

  • KumoRFM runs as an NVIDIA NIM. This demo talks to a hosted deployment; you can equally run the container yourself and point at localhost:8000.
  • The SDK is nvidia-sdfm[kumorfm], installed from NVIDIA's internal index. The kumorfm wheels are linux/amd64 only, so on Apple Silicon this runs inside a container.
  • The API key is never in the code. It is read from the environment, and the SDK sends it as an X-API-Key header. The SDK refuses to send a key to a remote plaintext endpoint.
  • The key stays server-side. The browser never sees it — the dashboard calls this server, and this server calls KumoRFM.
# .env, never committed
KUMORFM_NIM_URL=https://rfm-nim.dev.kumoai.cloud
KUMORFM_API_KEY=<your key>

# install (VPN required)
pip install --index-url https://urm.nvidia.com/.../nv-shared-pypi/simple \
    "nvidia-sdfm[kumorfm]==0.2.1" "kumorfm==2.28.0"

Invocation · what actually runs

Build the graph once, then query it

  • The graph is built and bound once at startup — roughly 6,800 nodes and 26,000 edges — not per request.
  • Each prediction is a single model.predict() call carrying the PQL string, the entity ids, and the anchor time.
  • indices takes a list, so scoring all 200 customers is one call, not 200.
  • The server computes nothing. It builds the query, sends it, and displays what came back.
# once, at startup
from nvidia_sdfm import SDFMClient, kumorfm

graph = kumorfm.Graph.from_data({
    "customers": customers, "products": products,
    "transactions": transactions,
})
graph["transactions"].time_column = "transaction_date"

client = SDFMClient(URL, KEY)
model  = client.kumorfm(graph)

# per prediction
df = model.predict(
    "PREDICT COUNT(transactions.*, 0, 90, days)=0 "
    "FOR EACH customers.customer_id",
    indices=["C055"],
    run_mode="fast",
    anchor_time=pd.Timestamp("2024-01-30"),
)

The four queries

# Churn — will they go quiet?
PREDICT COUNT(transactions.*, 0, 90, days)=0  FOR EACH customers.customer_id

# Engagement — will they buy at all?
PREDICT COUNT(transactions.*, 0, 30, days)>0  FOR EACH customers.customer_id

# Spend forecast — how much?
PREDICT SUM(transactions.amount, 0, 30, days) FOR EACH customers.customer_id

# Recommendation — what next? (link prediction over the product foreign key)
PREDICT LIST_DISTINCT(transactions.product_id, 0, 30, days)
        RANK TOP 5 FOR EACH customers.customer_id

How the model reads it

  • Each table needs a primary key so entities can be identified.
  • Foreign keys become graph edges. KumoRFM infers them from the schema — it detected transactions.customer_id ↔ customers.customer_id on its own.
  • Every table carries a time column. That is what makes anchor time work — the model can restrict itself to events before any given date.
  • transaction_date is the important one: it is the event timeline everything is predicted against.
graph = kumorfm.Graph.from_data({
    "customers": customers,
    "products": products,
    "transactions": transactions,
})
graph["transactions"].time_column = "transaction_date"

Why the shape matters

  • Churn, engagement and spend only need the customers ← transactions edge.
  • Recommendations need the products table. LIST_DISTINCT must target a foreign key. Pointing it at a plain category string fails with "Foundation Model queries do not support multilabel tasks."
  • The two-hop path customer → transaction → product → transaction → customer is what lets the model recommend something a customer has never bought — the signal arrives through other customers who share products.
