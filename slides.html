What we're looking at

One graph. Many questions.
No model training.

KumoRFM is a pre-trained foundation model for relational data. You point it at linked tables, write a predictive query, and it answers — no feature engineering, no training run, no per-task model.

Traditional ML
  • Flatten tables into one wide row per entity
  • Hand-build features (recency, frequency, ratios)
  • Train a separate model per question
KumoRFM
  • Keeps the tables and their foreign keys
  • Learns from the graph structure directly
  • New question = new query, same model
Why it matters here
  • Churn, engagement, spend and recommendations from one graph
  • Signal can come from other customers' behaviour, not just your own rows

The queries

Four questions, one line each

Predictive Query Language. Same graph, same model — only the query changes. Each returns a calibrated result per customer.

# Churn — will they go quiet?
PREDICT COUNT(transactions.*, 0, 90, days)=0  FOR EACH customers.customer_id

# Engagement — will they buy at all?
PREDICT COUNT(transactions.*, 0, 30, days)>0  FOR EACH customers.customer_id

# Spend forecast — how much?
PREDICT SUM(transactions.amount, 0, 30, days) FOR EACH customers.customer_id

# Recommendation — what next? (link prediction over the product FK)
PREDICT LIST_DISTINCT(transactions.product_id, 0, 30, days)
        RANK TOP 5 FOR EACH customers.customer_id
Anchor time is a first-class parameter. The model builds context only from events before the anchor and predicts the window after it — which is what prevents leakage. The demo exposes it as a slider.

Scope

What's real, and what isn't

Real
  • The model. Every number in the prediction panel is returned by KumoRFM running as an NVIDIA NIM.
  • The queries. The PQL shown on screen is exactly what is sent.
  • The SDK path. nvidia-sdfm[kumorfm] → hosted endpoint. No mocking.
  • Anchor time. A genuine model parameter, not a UI effect.
Not real
  • The data. 100% synthetic and seeded — customers, products, districts and managers are invented.
  • The business. District risk profiles were generated to make the rollup interesting.
  • The graph visuals. They depict the model's input, not its internal attention.
  • Confidence. Aggregates sum point estimates; no error bars.
What this demo is for: showing how a relational foundation model is queried and how its output lands in a decision-maker's hands — from a company-level summary down to one customer's neighbourhood. What it is not: a benchmark, an accuracy claim, or a validated business case.

  • Risk clusters by district rather than scattering.
  • A recommendation for a product the customer has never bought — that signal can only come from other customers.
  • Sliding the anchor back shrinks the context and changes the answer.
